# VTBIH — развёртывание и эксплуатация

Версия системы: **1.5.1**. Целевой способ установки — Docker Compose, три контейнера на одной машине.

Смежные документы: [руководство пользователя](user-guide.md), [архитектура](architecture.md).

---

## 1. Требования

| Ресурс | Минимум | Комментарий |
|---|---|---|
| ОС | Windows 10+ / Linux | проверено на Windows 11 и Debian |
| Docker | 24+ с Compose v2 | проверено на 28.1.1 / Compose 2.35 |
| ОЗУ | 8 ГБ, желательно 16 ГБ | OCR держит модели в памяти |
| Диск | **25 ГБ** свободно | образ конвертера один занимает 15,6 ГБ |
| Ядра | 4+ | распознавание идёт на процессоре |

Размеры образов после установки: `docling-serve` — 15,6 ГБ, `postgres:16-alpine` — 419 МБ, `vtbih-api` — 388 МБ. Плюс около 900 МБ в томе моделей OCR. Первая сборка тянет образ конвертера целиком, это занимает от десяти минут до часа в зависимости от канала.

Сеть: наружу нужен доступ к реестрам образов (`ghcr.io`, Docker Hub) при установке и обновлении. Языковая модель может быть в локальной сети — тогда интернет для работы не требуется вообще.

## 2. Установка

### Шаг 1. Файл настроек

```powershell
git clone <репозиторий> vtbih
cd vtbih
copy .env.example .env
```

Откройте `.env` и проверьте два параметра. Остальные можно оставить как есть.

```ini
# Адрес языковой модели. Здесь указана офисная машина в LAN.
SUMMARY_API_BASE_URL=http://192.168.215.74:9080/v1
SUMMARY_MODEL=Qwen/Qwen3.5-35B-A3B-FP8

# Пароль базы. Для контура вне доверенной сети — смените.
POSTGRES_PASSWORD=vtbih
```

### Шаг 2. Запуск

Windows:

```powershell
.\deploy.ps1
```

Linux:

```bash
chmod +x deploy.sh
./deploy.sh
```

Скрипты делают одно и то же: создают `.env` из примера, если его нет, и выполняют `docker compose up --build -d`. Можно вызвать эту команду напрямую.

### Шаг 3. Кириллическая модель OCR (обязательно)

В образе `docling-serve:latest` есть модели распознавания для латиницы и английского, но **нет кириллической**, а загрузка моделей в рантайме в образе отключена. Без этого шага любой отсканированный PDF на русском языке будет падать на первом этапе обработки с сообщением вида:

```
Missing .cache/docling/models/EasyOcr/cyrillic_g2.pth and downloads disabled
```

Догрузите модель один раз после первого запуска. Команда работает и в PowerShell, и в bash:

```bash
docker compose exec docling python -c "import easyocr; easyocr.Reader(['ru','en'], model_storage_directory='/opt/app-root/src/.cache/docling/models/EasyOcr', download_enabled=True, gpu=False)"
```

Скачивается около 100 МБ, занимает меньше минуты. Проверка:

```bash
docker compose exec docling ls /opt/app-root/src/.cache/docling/models/EasyOcr
# ожидается: craft_mlt_25k.pth  cyrillic_g2.pth  english_g2.pth  latin_g2.pth
```

Модель сохраняется в томе `vtbih-docling-models` и переживает пересоздание контейнера и обновление образа. Повторить шаг нужно только на новой машине или после `docker compose down -v`. Дальше интернет для распознавания не нужен.

### Шаг 4. Устройство разбора: процессор или GPU

По умолчанию разбор идёт **на процессоре**, и на большинстве машин это правильный выбор. Наличие видеокарты само по себе ничего не решает — проверьте замером, прежде чем включать GPU.

Почему нельзя решать по железу. На домашней машине с RTX 3080 Ti синтетический тест показал, что карта считает матричное умножение в 48 раз быстрее процессора. При этом один и тот же скан PDF на 2,4 МБ конвертировался **845 секунд на GPU против 420 секунд на 24-ядерном процессоре** при полностью одинаковом результате — 668 тысяч символов Markdown. Причина в том, что у docling ускоряется не весь конвейер: распознавание и определение разметки уходят на карту, а сборка структуры таблиц остаётся на процессоре и на многоядерной машине выигрывает. Под WSL2 добавляется то, что карта делится с рабочим столом.

Отсюда правило: устройство выбирается **измерением на документе, похожем на рабочий**.

```powershell
.\scripts\bench-docling.ps1 -File "C:\договоры\типовой-скан.pdf" -Apply
```

Скрипт по очереди поднимает конвертер на процессоре и на GPU, прогоняет один и тот же файл, печатает время каждого прогона и с ключом `-Apply` записывает победителя в `.env` как `VTBIH_DEVICE`. Дальше `deploy.ps1` и `deploy.sh` подхватывают это значение сами. Берите именно скан: «цифровой» PDF или xlsx не задействуют OCR, и разница между устройствами не проявится.

Переключить вручную:

```ini
# .env
VTBIH_DEVICE=gpu          # или cpu
DOCLING_NUM_THREADS=8     # только для процессора, по умолчанию по числу ядер, максимум 8
```

Разовый запуск без правки `.env`:

```powershell
$env:VTBIH_DEVICE = 'gpu'; .\deploy.ps1
```

GPU подключается оверлеем `docker-compose.gpu.yml`, который добавляет контейнеру карту и выставляет `DOCLING_DEVICE=cuda`. Устройство задано явно, а не через `auto`: при поломке проброса разбор упадёт с понятной ошибкой, а не уйдёт молча на процессор. Перед подключением скрипты проверяют, что карта действительно доезжает до контейнера, и при неудаче откатываются на процессор с предупреждением.

Требования для GPU: NVIDIA с актуальным драйвером и работающий проброс в Docker — на Windows это Docker Desktop с WSL2, на Linux NVIDIA Container Toolkit. Отдельный образ не нужен: в `docling-serve:latest` уже лежит PyTorch, собранный с CUDA.

### Шаг 5. Проверка

```bash
curl http://localhost:8080/api/health
```

Ожидаемый ответ — `ok: true`, `db.ok: true`, `pipeline.docling.ok: true`, `pipeline.llm.ok: true`. Признак `pipeline.llm.ok: false` при недоступной модели **не является отказом сервиса**: HTTP-код 200 зависит только от базы данных, с карточками можно работать и без модели.

Чек-лист приёмки:

- [ ] `http://localhost:8080` открывает интерфейс
- [ ] `/api/health` отдаёт `ok: true`
- [ ] в верхней панели интерфейса чипы «API», «Docling» и модель зелёные
- [ ] в томе моделей лежит `cyrillic_g2.pth`
- [ ] загрузка тестового PDF на русском доходит до состояния «MD готов»
- [ ] нажатие «Пересобрать поля» заполняет карточку

## 3. Что получилось после установки

```
vtbih-api-1        vtbih-api:1.5.1          0.0.0.0:8080->8080/tcp
vtbih-postgres-1   postgres:16-alpine       5432/tcp, только внутри сети
vtbih-docling-1    docling-serve:latest     0.0.0.0:5001->5001/tcp
```

Наружу обязателен только порт **8080** — контейнер `api` отдаёт и интерфейс, и API. Порт 5001 опубликован для диагностики конвертера; в закрытом контуре его публикацию можно убрать из `docker-compose.yml`. Порт базы наружу не выставлен вовсе.

Тома с данными:

| Том | Содержимое | Потеря означает |
|---|---|---|
| `vtbih-pg` | база: карточки, пользователи, настройки, CRM, инфоповоды | полную потерю данных |
| `vtbih-data` | загруженные файлы и результаты конвертации в `.md` | потерю исходников, карточки останутся |
| `vtbih-docling-models` | модели распознавания | необходимость повторить шаг 3 |

`docker compose down` тома не удаляет. Удаляет только `docker compose down -v` — эту команду на рабочем контуре выполнять нельзя.

## 4. Переменные окружения

Файл `.env` в корне репозитория. Читается собственным парсером (`server/config.js:7-27`), который **не перезаписывает** уже установленные переменные окружения.

### Обязательные

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL | нет; **без неё процесс завершается** |
| `PORT` | порт HTTP | `8080` |
| `DATA_DIR` | корень для файлов | `<репозиторий>/data`, в Docker `/app/data` |

### Конвертация документов

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DOCLING_URL` | адрес docling-serve | `''` — без него PDF, DOCX, XLSX не обрабатываются |
| `DOCLING_TIMEOUT_MS` | общий бюджет на конвертацию одного файла | `900000` (15 минут) |
| `DOCLING_TABLE_MODE` | режим разбора таблиц | `accurate` |
| `VTBIH_DEVICE` | устройство разбора: `cpu` или `gpu`; читают скрипты запуска | `cpu` |
| `DOCLING_DEVICE` | устройство внутри контейнера; выставляют скрипты, вручную не нужна | `cpu`, оверлеем — `cuda` |
| `DOCLING_NUM_THREADS` | потоков на процессоре; скрипты ставят по числу ядер, максимум 8 | `4` |

### Языковая модель

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `SUMMARY_API_BASE_URL` | базовый адрес локальной модели | `''` |
| `SUMMARY_MODEL` | имя модели | `Qwen/Qwen3.5-35B-A3B-FP8` |
| `SUMMARY_API_KEY` | токен, если модель его требует | `''` |
| `SUMMARY_ENABLE_THINKING` | режим «размышлений» Qwen | `false` |
| `LLM_TEMPERATURE` | температура | `0.1` |
| `LLM_MAX_TOKENS` | лимит ответа | `8192` |
| `LLM_MAX_DOC_CHARS` | обрезка Markdown перед отправкой | `80000` |
| `LLM_TIMEOUT_MS` | **только сторож мониторинга СМИ**, к разбору документов не применяется | `300000` |

Ключи облачных провайдеров (OpenAI, Claude, Gemini и прочие) в `.env` не прописываются — они задаются в интерфейсе и хранятся в базе.

### Прочее

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `BRAVE_SEARCH_API_KEY` | платный поиск для мониторинга СМИ | `''`, тогда работают RSS и бесплатный веб-поиск |
| `POSTGRES_PASSWORD` | пароль базы; читается **только** `docker-compose.yml` | `vtbih` |

Устаревшие синонимы, которые код всё ещё принимает: `LLM_API_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_ENABLE_THINKING`, `SUMMARY_TEMPERATURE`, `SUMMARY_MAX_TOKENS`. В новых установках использовать не нужно.

Особенность парсера: значения `0` и нечисловой мусор молча заменяются значением по умолчанию, поэтому обнулить таймаут через переменную нельзя.

## 5. Первичная настройка через интерфейс

**Авторизация выключена по умолчанию** — система открыта всем, у кого есть доступ к порту. Для контура шире доверенной сети включите её: «Настройки» → «Работа по авторизации» → галочка «Включить авторизацию». После этого откроется экран создания первого пользователя, он автоматически станет администратором и сможет приглашать остальных.

Ссылки-приглашения **не отправляются письмом**, даже если SMTP настроен. Администратор копирует ссылку из интерфейса и передаёт её сам.

**Выбор модели**: «Настройки» → «Откуда брать модель». Вариант «Локальная сеть» использует адрес из `.env`, менять его через интерфейс нельзя — только через `.env` и перезапуск. Вариант «Облако» требует ключа, который вводится в интерфейсе и попадает в базу. Кнопка «Сохранить и проверить» отправляет тестовый запрос и показывает задержку.

**Почта CRM**: «CRM» → «Почта SMTP». Настройки хранятся в базе, менять их может только администратор.

## 6. Обновление

```bash
git pull
docker compose up --build -d
```

Схема базы разворачивается идемпотентно при каждом старте, но **менеджера миграций нет**: если в новой версии изменился набор колонок, потребуется ручное вмешательство. Изменения внутри полей `payload` (а это большая часть модели данных) обратно совместимы и обновления не требуют.

Тег образа задан в `docker-compose.yml` (`image: vtbih-api:1.5.1`) и совпадает с `version` в `package.json`. При выпуске новой версии поднимайте оба значения синхронно — иначе `docker compose up` поднимет старый образ, не пересобрав его. Именно этот рассинхрон однажды привёл к тому, что контейнер работал на предыдущей версии, хотя код в репозитории был свежий.

Перед обновлением убедитесь, что нет активных разборов: корректного завершения в приложении нет, при остановке контейнера выполняющиеся задачи теряются, а их записи остаются в базе со статусом `running` и при старте не закрываются.

## 7. Резервное копирование и перенос на другую машину

Данные приложения лежат в томах Docker, а не в репозитории, поэтому `git pull` их не переносит. Снимок делает один скрипт:

```powershell
.\scripts\backup-data.ps1
```

Он складывает в `backup\vtbih-data-<дата>.zip` три вещи: дамп базы (`db.sql` — карточки, записки, промпты, настройки, CRM, пользователи), архив тома `vtbih-data` (исходные файлы проектов и собранный по ним Markdown) и кириллическую модель OCR из шага 3, чтобы её не пришлось качать заново. Для машины, где модель уже есть, добавьте `-SkipOcrModel`.

Развёртывание на второй машине — три шага по порядку:

```powershell
git pull                                              # код
.\deploy.ps1                                          # собрать и поднять контейнеры
.\scripts\restore-data.ps1 -Archive <путь к zip>      # данные
```

Если код через GitHub не возите — репозиторий публичный, а часть материалов выкладывать нельзя, — соберите всё одним архивом:

```powershell
.\scripts\make-transfer.ps1
```

В `backup\vtbih-transfer-<дата>.zip` попадут история git целиком (`code.bundle`), `.env` и слепок данных. Документы заказчика и коммерческие расчёты хранятся вне папки проекта, поэтому их добавляют явно: `-Documents <путь к папке>`. Внутри архива лежит `ЧИТАЙ-МЕНЯ.txt` с порядком действий. На принимающей машине история подтягивается прямо из файла:

```powershell
git pull <путь>\code.bundle main     # в существующий проект
git clone <путь>\code.bundle VTBIH   # если проекта ещё нет
```

`restore-data.ps1` останавливает API, пересоздаёт схему `public`, заливает дамп, заменяет содержимое тома с файлами и поднимает систему обратно. Всё, что было в базе на этой машине, теряется — поэтому скрипт спрашивает подтверждение (снять вопрос: `-Force`).

Архив содержит хеши паролей пользователей и рабочие настройки подключений, а `.env` в репозиторий не входит вовсе. Носите архив как рабочий документ и не выкладывайте его в репозиторий: папка `backup/` для этого добавлена в `.gitignore`. На новой машине `.env` создаётся из `.env.example` при первом запуске `deploy.ps1` — сверьте в нём адрес LLM и `VTBIH_DEVICE`.

Если нужен только дамп базы, без файлов и скриптов:

```bash
docker compose exec -T postgres pg_dump -U vtbih -d vtbih --clean --if-exists -f /tmp/db.sql
docker compose cp postgres:/tmp/db.sql ./db.sql
docker compose exec -T postgres psql -U vtbih -d vtbih -f /tmp/db.sql   # обратно
```

Дамп пишется файлом внутри контейнера и забирается через `docker compose cp` намеренно: перенаправление вывода `pg_dump` в файл средствами PowerShell портит кодировку русского текста.

## 8. Остановка и удаление

```bash
docker compose down            # остановить, данные сохранить
docker compose down -v         # ОПАСНО: удалить вместе с базой и файлами
docker compose restart api     # перезапустить только API
docker compose logs -f api     # смотреть журнал
```

## 9. Разработка без Docker

Нужны Node.js 22 и PostgreSQL — либо локально, либо только контейнер базы из compose.

```bash
npm install

# конвертер отдельным контейнером
docker run --rm -p 5001:5001 ghcr.io/docling-project/docling-serve:latest

# в .env заменить адреса на локальные
# DOCLING_URL=http://localhost:5001
# DATABASE_URL=postgres://vtbih:vtbih@localhost:5432/vtbih

npm run dev:api    # API на 8080
npm run dev        # интерфейс на 5173, проксирует /api на 8080
```

Открывать нужно `http://localhost:5173`. В этом режиме статика отдаётся Vite с горячей перезагрузкой, а блок `express.static` в API не активируется, так как каталога `dist` нет.

Отдельному контейнеру конвертера тоже нужна кириллическая модель — команда из шага 3 применима к нему по имени контейнера.

Остальные команды:

```bash
npm test           # 423 теста, Vitest
npm run test:watch
npm run build      # tsc + vite build, обязательно перед сборкой образа
```

## 10. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `/api/health` не отвечает, контейнер перезапускается | нет `DATABASE_URL` или база не поднялась | `docker compose logs api`, искать `[db]`; проверить состояние `postgres` |
| Обработка PDF падает за секунды, «Ошибка на этапе Docling» | нет кириллической модели OCR | выполнить [шаг 3](#шаг-3-кириллическая-модель-ocr-обязательно) |
| «Ошибка на этапе Docling» на всех форматах | конвертер недоступен | `docker compose ps docling`, проверить `DOCLING_URL` |
| «Ошибка на этапе модели — Markdown уже создан» | модель недоступна или вернула мусор | проверить чип модели в интерфейсе, нажать его для тестового запроса |
| Чип модели «нет», ошибка `UND_ERR_CONNECT_TIMEOUT` | адрес модели недостижим из контейнера | вне офисной сети это норма; для модели на том же хосте использовать `http://host.docker.internal:9080/v1` |
| Карточка заполнилась мусором из имени файла | модель не настроена, сработала эвристика | настроить модель, нажать «Пересобрать поля» |
| Развернули новую версию, изменений нет | тег образа в `docker-compose.yml` не подняли | синхронизировать тег с `package.json`, пересобрать |
| Долгая обработка, десять минут и больше | распознавание на процессоре | норма: скан 2,4 МБ распознаётся около 7 минут, дальше работает модель |
| Включили GPU, стало медленнее | часть конвейера docling не ускоряется картой | замерить и вернуть процессор: `.\scripts\bench-docling.ps1 -File <скан> -Apply` |
| `could not select device driver` при запуске | подключён GPU-оверлей на машине без проброса карты | убрать `VTBIH_DEVICE=gpu` из `.env`; скрипты запуска проверяют это сами |
| Настройки модели «разъезжаются» | запущено больше одного экземпляра API | оставить один: настройки кэшируются в памяти процесса |
| Задачи висят в статусе `running` | контейнер перезапустили во время разбора | нажать «Пересобрать поля» заново; висящие записи безвредны |
| В интерфейсе «лок. кэш» вместо «API» | браузер не видит API | проверить порт 8080 и `VITE_API_URL`, если фронтенд собран отдельно |

Полезные команды:

```bash
docker compose logs --tail 200 api
docker compose logs --tail 200 docling
docker compose exec postgres psql -U vtbih -d vtbih -c "select id, status, stage, created_at from llm_jobs order by created_at desc limit 10;"
curl http://localhost:8080/api/health/llm?refresh=1
```

## 11. Эксплуатационные замечания

Их стоит учитывать при планировании контура. Подробное обоснование — в [архитектуре](architecture.md#16-известные-ограничения-и-технический-долг).

**Один экземпляр API.** Настройки модели, почты и флаг авторизации кэшируются в памяти процесса и обновляются только собственной записью. Горизонтальное масштабирование приведёт к расхождению настроек между репликами. Масштабировать можно только вертикально.

**HTTPS через обратный прокси.** Cookie сессии выставляется без флага `Secure`, а CORS отражает любой источник с разрешением на передачу cookie. Публиковать сервис за пределы доверенной сети следует только за прокси, терминирующим TLS.

**Секреты в базе открытым текстом.** Ключ облачной модели и пароль SMTP лежат в `app_settings` без шифрования. Дамп базы содержит их и требует обращения как с секретом.

**Перезапуск во время разбора.** Активные задачи и открытые потоки событий теряются без корректного завершения. Плановые перезапуски лучше проводить, когда список объектов не содержит проектов в состоянии «Расчёт».

**Загрузки не ограничены по объёму.** Лимит есть только на один файл — 40 МБ. Ротации и вытеснения старых файлов в томе `vtbih-data` нет, за его размером нужно следить самостоятельно.
